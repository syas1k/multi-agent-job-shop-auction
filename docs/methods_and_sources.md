# Методы, источники и границы воспроизведения

## Что реализовано

Реализация сохраняет Environment, JobAgent, MachineAgent и ManagerAgent. Добавлены
классические правила диспетчеризации и явная адаптация ATC. Это не воспроизведение
полного эксперимента какой-либо статьи и не реализация аукционного протокола Wellman.

Все методы принимают решения только для операций, доступных в текущий момент.
Прерываний нет; станок у операции фиксирован; операций с нулевой длительностью нет.
Поломки пока не моделируются: заблокированная среда выдаёт ошибку вместо бесконечного цикла.
Будущие поступления хранятся в среде, но недоступны правилам выбора и ставкам до release_time.
Диспетчеризация не оставляет станок намеренно простаивать, если есть доступная операция.

Обозначения: t — время, p — длительность текущей операции, R — сумма длительностей
текущей и последующих операций заказа, d — дедлайн, a — время входа в очередь
текущего станка. Для первой операции a=release_time, для остальных — завершение предыдущей.

| Метод | Критерий выбора | Статус |
|---|---|---|
| FIFO | минимум a | Стандартное правило очереди; прежний выбор по job_id исправлен |
| EDD | минимум d | Стандартное правило; отсутствие дедлайна обозначается бесконечностью |
| SPT | минимум p | Стандартное правило кратчайшей операции |
| MWKR | максимум R | Стандартное правило Most Work Remaining |
| CR | минимум (d-t)/R | Critical Ratio с оставшейся обработкой без оценки ожидания |
| ATC_LOCAL | максимум exp(-max(d-t-R,0)/(k*p_mean))/p | Адаптация, определённая ниже |
| CENTRAL_ORIGINAL | максимум R + 100/max(d-t, 1e-6) | Исходная формула проекта |
| AUCTION_ORIGINAL | та же ставка через агентов | Исправлен допуск операций |
| AUCTION_ATC | индекс ATC_LOCAL через агентов | Адаптация стратегии ставки |

При равных приоритетах выбирается меньший (job_id, op_index); порядок станков фиксирован.
ATC_LOCAL в коде использует логарифм индекса: он сохраняет порядок и не страдает от
обнуления экспоненты. Отрицательные значения Bid.value допустимы: это приоритеты, не деньги.
p_mean — средняя длительность доступных операций на данном станке в данном раунде;
k=2 по умолчанию, параметр доступен в CLI. Все веса заказов равны 1.

## Как именно адаптирован ATC

Базовая формула ATC для доступных работ:
I = (w/p) * exp(-max(d-t-p, 0)/(k*p_mean)).
Её явная запись доступна в Lamothe et al., формула (1).
Для маршрута из нескольких операций здесь выбран локальный срок
d_local = d - (R-p), то есть из дедлайна вычитается только последующая обработка.
Подстановка даёт запас d-t-R. Ожидание на следующих станках не оценивается.
Это наш вариант ATC_LOCAL, а не полная реализация look-ahead-правил
Vepsalainen & Morton. Из их статьи проверены библиографические сведения и аннотация;
полный текст оригинала при реализации не использовался.

Если дедлайна нет, ATC_LOCAL сводится к SPT. В исходной формуле проекта компонент
срочности в этом случае равен нулю, и правило сводится к MWKR.
Поэтому нельзя считать эти совпадения независимыми победами аукционного метода.

Аукцион здесь однораундовый: заявки, выбор максимума, назначение.
Цены, бюджеты, стратегическое поведение, равновесие и восходящий торг не реализованы.
CENTRAL_ORIGINAL и AUCTION_ORIGINAL, а также ATC_LOCAL и AUCTION_ATC
должны давать одинаковые расписания. Программа проверяет это по хешам всех интервалов.

   Основа обсуждения приоритетов с учётом сроков и оставшегося маршрута.

   Scheduling rules to minimize total tardiness in a parallel machine problem with

   Auction Protocols for Decentralized Scheduling.** Games and Economic Behavior,

   [DOI](https://doi.org/10.1006/game.2000.0822),
   [страница исследовательской группы](https://strategicreasoning.org/publications/2001/auction-protocols-for-decentralized-scheduling/),

   Для теоретического раздела об аукционной координации. Механизм этой статьи
   отличается от локального выбора по ставке в нашем проекте и не реализован.

## Существующие программные решения и данные

- [JobShopLib: dispatching rules](https://job-shop-lib.readthedocs.io/en/latest/api/job_shop_lib.dispatching.rules.html):
  первичная документация существующей реализации SPT и MWKR. Их определения
  использованы как дополнительная проверка. Зависимость JobShopLib не добавлялась,
  её исходный код не копировался.
- [JSPLIB](https://github.com/tamy0612/JSPLIB):
  нормализованные статические задачи FT, LA, ABZ, Taillard и метаданные оптимумов/границ.
  Данные скачиваются без изменения; URL, commit и SHA-256 сохранены в manifest.json.
  Это внешние исследовательские данные, не код проекта под MIT.
  Исходный формат Taillard с отдельными матрицами загрузчик не поддерживает —
  используются нормализованные пары станок–длительность из JSPLIB.

## План эксперимента

Девять экземпляров: ft06, ft10, ft20, la01, la16, la31, abz5, ta51, ta71.
Девять методов, 14 сценариев на экземпляр при seeds=5: всего 1134 прогона.

- static: исходные длительности и маршруты; все поступают в 0, дедлайнов нет.
- due_dates: все поступают в 0; d = release_time + factor * total_job_processing,
  factor = 1.5, 2, 3.
- arrivals: release_time равномерно распределено на [0, total_work / machine_count];
  factor = 1.5, 2; seed = 0..4.

Сроки и поступления синтетические, созданные нами поверх JSPLIB. Это конечная партия,
не исследование стационарной загрузки. Все методы получают одинаковую задачу в каждой паре.
Коэффициенты не подбирались по результатам тестовых экземпляров.

Сохраняются makespan, суммарное опоздание, доля просроченных заказов,
среднее время пребывания, фактическая загрузка, время алгоритма, число заявок и аукционов.
Без сроков показатели опоздания отсутствуют, а не равны «доказанному нулю».
Gap к известному оптимуму считается только для исходного static makespan.
Времена вычислений — одиночные измерения, не доказательство преимущества по скорости.
Пять seed и описательные средние не заменяют статистический анализ:
для итоговой главы нужны больше независимых сценариев, парные интервалы
и отдельная проверка чувствительности k, сроков и интенсивности поступлений.

## Воспроизведение

Из корня проекта после установки python -m pip install -e ".[dev]":

```powershell
python -m pytest
python scripts/download_benchmarks.py
python scripts/run_benchmarks.py
python scripts/plot_benchmarks.py
python run_experiment.py data/benchmarks/ft10.txt --scenario arrivals --seed 0
```

В этой Windows-среде HTTPS из Python завершался по тайм-ауту; эквивалентный загрузчик:

```powershell
./scripts/download_benchmarks.ps1
```

Для точного повторного скачивания передать сохранённый commit:
--revision <commit> в Python или -Revision <commit> в PowerShell.
Если файлы уже скачаны, для повторения эксперимента сеть не нужна.
