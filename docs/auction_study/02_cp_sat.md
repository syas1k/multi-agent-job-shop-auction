# 2. CP-SAT: что это и как читать реализацию

## Чем он отличается от FIFO и ATC

FIFO и ATC выбирают следующую операцию по правилу. CP-SAT рассматривает множество возможных расписаний и ищет вариант с меньшей целевой величиной при соблюдении ограничений.

Нейросети и обучения здесь нет. Это централизованный оптимизатор из OR-Tools. Наша работа — сформулировать для него производственную задачу и корректно встроить вызов в эксперимент.

Источник модели: [официальное объяснение Job Shop в OR-Tools](https://developers.google.com/optimization/scheduling/job_shop).
Описание ограничений и статусов: [CP-SAT Solver](https://developers.google.com/optimization/cp/cp_solver).

## Шаг 1. Приводим время к целым тактам

CP-SAT работает с целыми числами. Наши случайные поступления и сроки дробные, поэтому quantize_jobs в [cp_scheduler.py](../../src/mas_jssp/cp_scheduler.py) переводит время:

```text
такты = floor(время × scale + 0.5)
```

При scale=10 сохраняется точность примерно до десятой единицы. Например, 1,26 превращается в 13 тактов, то есть 1,3.

Важно: ту же округлённую задачу получают FIFO, ATC и все аукционы. Иначе сравнивались бы разные условия. Это не точная копия прошлых экспериментов с дробными временами.

## Шаг 2. Создаём неизвестные начало и конец

```python
start = model.new_int_var(earliest, horizon, ...)
end = model.new_int_var(earliest, horizon, ...)
interval = model.new_interval_var(start, int(op.duration), end, ...)
```

start и end пока не конкретные моменты, а неизвестные величины. Интервал задаёт связь: конец равен началу плюс длительность.

earliest — раньше какого момента начинать нельзя. horizon — достаточно поздний предел, в который помещается даже последовательное выполнение оставшейся работы.

## Шаг 3. Задаём ограничения

```python
model.add(start >= previous_end)
model.add_no_overlap(own_intervals)
```

Первое условие: следующая операция ждёт предыдущую.

Второе: операции на одном станке не перекрываются во времени.

В онлайн-режиме нижняя граница начала учитывает занятость станка уже начатой операцией. Выполненные и начатые операции не переставляются.

## Шаг 4. Выбираем цель

Можно искать минимальный makespan либо минимальную сумму опозданий.

Для makespan берётся максимальное время завершения заказа.

Для опозданий у каждого заказа создаётся величина:

```text
late = max(0, конец заказа − срок)
```

Решатель минимизирует сумму late. Нормированное опоздание на одном сценарии имеет тот же минимум, поскольку деление на общий объём работы — постоянный множитель.

Если минимизируем опоздания, makespan не получает дополнительного приоритета: среди равных по опозданию решений он может отличаться. Нельзя ожидать автоматического выигрыша сразу по всем показателям.

## Шаг 5. Ограничиваем время поиска

На каждый вызов задаётся лимит секунд и один рабочий поток. Результаты:

- OPTIMAL — оптимальность доказана для данной модели.
- FEASIBLE — допустимое решение найдено, но оптимальность не доказана.
- UNKNOWN — допустимое решение не получено в пределах вызова.
- Другие статусы тоже сохраняются; ошибку нельзя выдавать за хорошее расписание.

Одно и то же ограничение реального времени на разных компьютерах может давать разные результаты, даже при одинаковом seed.

## Два режима — не смешивать

### CP_OFFLINE: вся партия известна заранее

Решатель получает все заказы, включая будущие поступления, и строит полное расписание. В динамической задаче это ориентир с преимуществом в информации.

Если он сообщает OPTIMAL, оптимально решение именно округлённой задачи с выбранной целью. FEASIBLE означает лишь найденное решение. Доступная нижняя граница сохраняется отдельно.

### CP_ONLINE: только уже поступившие заказы

При возможности назначения:

1. Берём только заказы, которые уже поступили.
2. Передаём их остаток оптимизатору.
3. Запускаем только те операции, которые план предлагает начать сейчас.
4. Будущие назначения не фиксируем навсегда: при следующем событии план пересчитывается.
5. Если решатель ничего не нашёл, явно используем ATC и увеличиваем счётчик fallback_calls.

Оптимизатор может оставить станок свободным в ожидании более выгодной операции известного заказа. Событие нового поступления прерывает ожидание, но сами будущие заказы не передавались решателю заранее.

Даже если каждый отдельный вызов имеет статус OPTIMAL, это не доказательство глобально оптимального онлайн-расписания: неизвестное будущее может изменить ситуацию.

## Как сравнивать с аукционами

Онлайн-решатель и агенты не видят будущих поступлений. Но CP-SAT централизованно видит полные маршруты поступивших заказов, а станки в аукционе — локальные предложения. Это сознательное различие архитектур, которое следует указать в выводах.

Время CP-SAT нужно учитывать полностью: много вызовов даже с небольшим лимитом может быть существенно дороже простых правил. Цель эксперимента — оценить компромисс качества и стоимости расчёта, а не заранее доказать победу одного подхода.
